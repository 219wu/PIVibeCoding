# 多角色落地：独立会话与角色分离

> 本协议把"审查者不是写代码的人"从提示词层面的建议，变成**可执行的独立会话流程**。
> 核心三支柱：角色分离（不同上下文）、模型分离（不同档位/厂商）、信息隔离（只吃输入包）。

## 一、为什么需要独立会话

同一会话里"让模型换个角色审查自己"仍然共享全部对话历史——
它看得到自己写代码时的乐观解释，无法真正"重新开始"。

**独立会话** = 新的上下文窗口，审查者只看到 `prepare_review.py` 生成的输入包，
看不到编写过程的任何中间产物。这是对抗同源幻觉最彻底的一步。

## 二、三个角色与模型

| 角色 | 职责 | 模型 | 会话 |
|------|------|------|------|
| **编写者 Writer** | 构思→执行→验证 | deepseek-v4-flash（默认） | 主会话 |
| **审查者 Reviewer** | 对抗性审查（只吃输入包） | deepseek-v4-pro（set_review_model 切换，或跨厂商） | **独立会话** |
| **验证者 Verifier** | 独立判定验收标准 | 可与编写者同模型 | 主会话（验证证据独立） |

## 三、操作流程

### 步骤 1：编写者完成执行阶段（主会话）

```bash
/skill:vibekit 实现 XX 功能
# ... 完成 构思/计划/隔离/执行/验证
```

### 步骤 2：生成审查输入包（主会话）

```bash
python ~/.pi/agent/skills/vibekit/scripts/prepare_review.py \
  --acceptance "验收标准1；验收标准2；..."
# 输出 .vibe/review/prompt.md（diff + 验收标准 + 审查指令，diff hash 防篡改）
```

### 步骤 3：开启审查者独立会话

```bash
# 方式 A：全新会话（推荐，最干净）
/new
# 或方式 B：克隆当前会话再清空编写过程（保留项目文件引用）
/clone

调用 set_review_model 工具切换审查模型
#   或手动: /model deepseek-v4-pro        # 切换审查模型（模型分离）
```

### 步骤 4：审查者只读输入包，按协议审查

给审查者的指令模板：

```
你是独立代码审查员（Critical Reviewer），不是编写者的助手。
只依据 .vibe/review/prompt.md 审查（diff hash: <填>），
按 ~/.pi/agent/skills/vibekit/references/review.md 协议执行：
默认假设有 bug、逐条证伪、每条发现带证据（文件:行）、主动找挂点。
结论写入 .vibe/review/review.md。
```

审查者**不得**：
- 查看编写者会话的任何内容（禁读对话历史、禁看编写者笔记）
- 接受编写者的口头解释作为证据
- 修改代码（只出报告；修复由编写者做，再审）

### 步骤 5：回写与修复循环

```bash
# 审查者完成报告后，回到主会话
/resume        # 选主会话
# 按审查报告修复 → 重新 prepare_review → 审查者再审（循环直到通过）
```

## 四、信息隔离的工程保证

1. **输入包机制**：`prepare_review.py` 机械打包 diff+验收标准+指令，
   **不含**编写者的自我解释（`--with-context` 显式标记为"单方陈述"）
2. **diff hash**：审查报告记录 hash，防止"审查后代码又改了但报告是旧的"
3. **.vibe/review/ 目录**：只有 prompt.md（输入）和 review.md（输出），
   不暴露编写过程
4. **git 状态**：审查时工作区即"执行阶段结束"的状态，可 `git diff HEAD` 复核

## 五、进阶：跨厂商审查

同厂分档（flash 写 / pro 审）已能规避大部分同源错误；
若审查仍频繁放行幻觉，可让审查者用**第二厂商**模型（如 Qwen / GLM）：
不同厂商的训练数据与错误模式不相关，交叉验证最彻底。
代价：多一个 API 配置（~/.pi/agent/auth.json 增加条目即可）。

## 六、验证者独立性

验证阶段（⑤）的结论也不应由编写者"口头宣布"：
- 运行测试/程序的**真实输出**就是证据（命令 + 退出码 + 输出）
- 框架调用参数传递：mock 拦截 payload（见 test-scenario/langchain-param-bug）
- 验证结论写入验证记录，审查者审的是"验证证据是否充分"，不是"编写者说通过了"
