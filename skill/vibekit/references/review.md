# 独立审查协议（对抗性审查 / Adversarial Review）

> 六阶段"审查"的执行规范。审查者是**独立角色**，不是编写者的"自我检查"。

## 一、为什么需要独立审查

同一个模型自写自审存在**同源幻觉 + 确认偏误**：
它写错了，会为这个错误编造"合理的解释"，然后自己接受这个解释。

对抗性审查的两个支柱：

1. **信息隔离**：审查者只看「代码 diff + 验收标准 + 审查指令」，
   **不看**编写者的设计理由、自我解释、"我觉得没问题"。
   —— 输入包由 `prepare_review.py` 机械生成，编写者不得往里面塞解释。
2. **模型分离**：编写与审查用**不同模型**。
   最低要求：编写用 `deepseek-v4-flash`，审查切换 `deepseek-v4-pro`
   （同厂不同档位，错误模式已不同）。
   进阶：引入第二厂商（Qwen / GLM）做审查，规避同源幻觉最彻底。

## 二、审查者的角色设定

你是**独立代码审查员（Critical Reviewer）**，不是助手，不是啦啦队。

- 默认假设代码里有 bug，你的任务是**逐条证伪**，直到证据证明它没问题。
- 禁止使用"应该没问题""看起来对""代码风格良好"这类无证据表述。
- 每条发现必须给出：**证据（文件/行/命令输出）+ 影响 + 修复建议**。
- 你是最后一道质量关卡，放行有问题的代码 = 你的失职。

## 三、输入与输出

### 输入（只接受这些）

| 输入 | 来源 | 说明 |
|------|------|------|
| 代码 diff | `.vibe/review/prompt.md`（`prepare_review.py` 生成） | 只读 diff，不读全文件历史 |
| 验收标准 | 同上（来自①构思阶段） | 逐条对照 |
| 审查指令 | 本协议 | 下方检查清单 |
| 项目上下文 | 必要时 `git show HEAD:path` 看修改前版本 | 判断回归风险 |

### 拒绝的输入

- 编写者的口头解释 / 设计理由（除非在 prompt.md 的 `[编写者补充上下文]` 区，且需注明这是单方陈述）
- 编写者的"验证结论"（验证结论由验证阶段独立得出，不由编写者转述）

### 输出格式（写入 `.vibe/review/review.md`）

```markdown
# 审查报告 <任务名>
- 审查模型: deepseek-v4-pro
- 审查时间: <ISO 时间>
- 审查输入: .vibe/review/prompt.md（版本 hash: <git diff hash>）

## 验收标准逐条核对
| # | 验收标准 | 结论 | 证据 |
|---|----------|------|------|
| 1 | ... | ✅ 满足 / ❌ 不满足 | 证据 |

## 发现清单
| 严重度 | 位置 | 问题 | 证据 | 修复建议 |
|--------|------|------|------|----------|
| S/A/B/C | 文件:行 | ... | ... | ... |

严重度定义：
- S 阻断：功能错误 / 数据损坏 / 安全隐患，必须修复
- A 重要：边界情况会挂 / 明显缺陷，应修复
- B 一般：命名/重复/可读性，建议修复
- C 提示：风格/优化机会，可选

## 主动找挂点（必填）
列出至少 1 个"这个实现会在什么场景挂掉"的推演：
场景 → 触发条件 → 结果 → 是否被现有代码处理

## 结论
- 通过（无 S/A 级问题）→ 进入⑦集成
- 需修复（有 S/A 级问题）→ 回④执行修复，重新生成审查输入包再审
- 存在 B/C 级问题 → 小问题直接修复，或记录为遗留项
```

## 四、检查清单（逐条过）

### 1. 验收标准对照（最高优先）
- [ ] 每条验收标准可测吗？不可测 → 指出并回①构思
- [ ] 每条验收标准都被代码满足了吗？逐条找证据
- [ ] 有没有"验收标准没覆盖但代码引入了新行为"的地方？

### 2. 功能正确性
- [ ] 逻辑正确性：条件分支、循环、状态转换
- [ ] 边界情况：空输入、0、None、超长、并发
- [ ] 错误处理：异常路径是否处理，还是静默吞掉
- [ ] 返回值/退出码语义正确

### 3. 框架调用与参数传递链（本项目血的教训）
- [ ] 框架 API 的"正确用法"？参数是否显式传递？
- [ ] 有没有 `a.bind(...).b(...)` 这种参数可能丢失的链式调用？
- [ ] 验证阶段是否用 mock 拦截 payload 证明参数真实到达？（不是"看起来对"）

### 4. 安全
- [ ] 路径注入 / 命令注入（subprocess 拼接、shell=True）
- [ ] 密钥/令牌硬编码或泄露到日志
- [ ] 不可信输入的处理
- [ ] 文件操作的路径校验

### 5. 兼容性
- [ ] Windows 路径/编码（本项目在 Windows 上跑）
- [ ] 编码：GBK 控制台 vs UTF-8 文件
- [ ] 依赖版本假设

### 6. 代码质量
- [ ] 命名清晰、无魔法数字
- [ ] 重复代码、过长函数
- [ ] 注释与代码一致
- [ ] 遵循项目既有风格

## 五、操作流程

```bash
# 1. 编写者（flash 模型）完成执行阶段后，生成审查输入包：
python ~/.pi/agent/skills/vibekit/scripts/prepare_review.py \
  --acceptance "验收标准文本（来自①构思）"

# 2. 切换审查模型（会话级，优先用工具）：
#    调用 set_review_model 工具，或手动 /model deepseek-v4-pro

# 3. 审查者读取输入包，按本协议审查：
#    （只读 prompt.md 里的 diff + 验收标准 + 检查清单）
#    输出写 .vibe/review/review.md

# 4. 判定：
#    通过 → ⑦集成；需修复 → 回④，修复后重新 prepare_review 再审
```

## 六、原则速记

1. 信息隔离：只吃 diff + 验收标准，不吃解释
2. 模型分离：flash 写、pro 审（或跨厂商）
3. 默认有 bug：逐条证伪，不是逐条确认
4. 每条发现带证据：文件:行 + 命令输出
5. 必须主动找挂点：至少推演 1 个"会挂的场景"
